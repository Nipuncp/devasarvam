## Frontend setup (from scratch, on a new machine)

1. Install Node.js LTS (Node 20 or 22) from nodejs.org.
2. Scaffold a fresh Vite project:
   ```
   cd D:\Devasarvam
   npm create vite@latest app -- --template react
   cd app
   npm install
   ```
3. Install the libraries the prototype uses:
   ```
   npm install lucide-react sql.js
   npm install -D tailwindcss@3 postcss autoprefixer
   ```
   Note: pinned to Tailwind v3. v4 has a different config style.
4. Replace the auto-generated files with the ones from this handoff:
   - `src/App.jsx` ← from `frontend/App.jsx`
   - `src/index.css` ← from `frontend/index.css`
   - `tailwind.config.js` ← from `frontend/tailwind.config.js` (project root)
   - `postcss.config.js` ← from `frontend/postcss.config.js` (project root)
   - Delete `src/App.css` (Vite default, not used).
5. Confirm `package.json` has `"type": "module"` (Vite adds it; check just in case).
6. `npm run dev` → http://localhost:5173

## Backend setup

1. Create the folder, init, install:
   ```
   cd D:\Devasarvam
   mkdir backend
   cd backend
   npm init -y
   ```
2. Edit `package.json` to set `"type": "module"` and add the scripts in this handoff's `backend/package.json`.
3. Install:
   ```
   npm install express cors
   npm install -D nodemon
   ```
4. Drop in `index.js` from this handoff.
5. `npm run dev` → http://localhost:3001
6. Visit `/` and `/health` to verify.

- All frontend modules render and are interactive: Daily Routine, Inventory, Store/Requisition, Purchase, Vazhipadu Counter (3 modes), Uthsavam, Data Entry.
- Persistence via browser `localStorage` (key: `temple-state`).
- SQLite export/import via `sql.js` npm package (locally bundled wasm via Vite `?url`).

- Receipt printing via `@media print` CSS isolation pattern.

## Architectural caveats — read before going deep

This is a **prototype**, not a production system. Specific limits:

- **Single-machine only.** The frontend runs in one browser, the backend on the same computer. There is no multi-user model. Two browsers will see independent localStorage state.
- **No authentication.** Anyone with network access to port 3001 can write any data.
- **No audit trail.** Edits and deletions leave no record.
- **No real disaster recovery.** Backups are files on the same disk; if the disk dies, data is gone.
- **CORS is wide open.** Fine for `localhost`; would need locking down for any real deployment.
- **Browser localStorage has a ~5MB limit** per origin. The current state will fit comfortably; large historical data won't.

If the goal is to actually run a temple's operations, this should be rebuilt by a development team with a proper DB (Postgres), proper auth, proper deployment, and proper backup strategy. We've been treating this prototype as a **living specification** to drive that conversation, not as the production system itself.

## File-by-file quick reference for App.jsx

The single ~7,200 line `App.jsx` is organized roughly:

- Lines 1–10: imports (React, lucide-react icons, sql.js)
- Lines 10–130: `SAMPLE DATA` constants (catalog, inventory, vendors, etc.)
- Lines 133–1300: main `TempleManagement` component — state, effects, render
  - Look for `// ===== ` comment markers as section headers
- Lines 1300+: child components (each tab is a function)
- Last section: `BackupReminder`, `Card`, small UI helpers

The frontend's SQLite export logic (in `DataEntry`) uses helper functions `writeTable` and `saveAsMeta`. These are a useful template for the backend's symmetric write logic — same shape, but server-side `better-sqlite3` instead of `sql.js`.
