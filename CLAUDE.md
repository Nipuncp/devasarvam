## What this repo is

Devasarvam — temple management software for Nelliakattu Oushadheeswari Temple, Kizhakombu, Kerala. Mid-migration from a single-file React prototype to a cloud-hosted (Vercel + Supabase) multi-device app with offline support and ESC/POS receipt printing.

The migration plan lives at `~/.claude/plans/breezy-wishing-harp.md` and is the canonical roadmap.

```bash
cp .env.example .env.local   # then fill VITE_SUPABASE_URL + VITE_SUPABASE_ANON_KEY
```


## How to wire a remaining module to Supabase

Pick a module and follow this recipe (matches what's already done for Uthsavam, DailyRoutine, Inventory):

1. Read the module's prop signature in `src/App.jsx` — know what data + callbacks it needs.
2. Find the corresponding hooks in `src/data/`. If a hook is missing, write it (see `src/data/CLAUDE.md` for the canonical pattern).
3. In the module file, drop the props and call hooks instead.
4. Map prototype field names (camelCase, `counterQty`, `unitCost`, `lastVerified`) to DB column names (snake_case: `counter_qty`, `unit_cost`, `last_verified`). Don't try to alias — rename throughout for clarity.
5. Gate write actions with `useRole()` (`src/lib/auth.jsx`).
6. Update the JSX call site in `src/App.jsx` to render `<Module />` with no props.
7. Build with `npm run build` and click through in `npm run dev`.
8. Schema gaps you find while wiring → new migration in `supabase/migrations/`. Apply via SQL Editor (CLI `db push` is flaky on Linux; SQL Editor is reliable).

## Load-bearing constraints (don't "fix" these without reading why)

- **Tailwind v3, not v4.** v4 has a different config style; pinned deliberately.
- **Print receipts use `@media print` CSS isolation** in `BillSlip` / `RetailReceipt` / `KioskSlip` / `IssueSlip`. Phase 4.5 adds ESC/POS as a layer in front; the browser-print path stays as the universal fallback.
- **`bills.id` is client-generated UUIDs**, not server-generated. Phase 4 offline-idempotency depends on this.
- **`inventory_movements` is append-only**. In Phase 4 it becomes the source of truth for `inventory_items.qty`.
- **Realtime requires explicit publication membership.** Adding a new table? Also add it to the `supabase_realtime` publication (see `0004_realtime_publication.sql`), or `postgres_changes` subscriptions silently won't fire.
- **Service-role key bypasses RLS.** Phase 1.5's import endpoint uses it server-side. Never expose it to the browser.
- **`.env.local` holds secrets** (anon/publishable key + service-role + db password + access token). Gitignored. Anon key is safe in the bundle; service-role is not.

## Common tasks

- **Add a vazhipadu / inventory item / retail item / etc.** — edit the JSON in `src/seed/`, run `npm run seed:generate`, commit both. See `src/seed/CLAUDE.md` for full rules. For live Supabase update, an admin uses the (planned Phase 1.5) Excel import UI; for code-driven sync, run `supabase db reset`.
- **Schema change** — new file in `supabase/migrations/`, applied via the dashboard SQL Editor (most reliable path). After applying, regenerate types if you've added them.
- **Bigger feature** — check the plan file first.
